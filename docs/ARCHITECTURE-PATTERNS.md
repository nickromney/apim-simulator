# Azure Architecture Center patterns that use API Management

**Inventory checked: 2026-10-01.** This is a dated reading map for the Microsoft Learn [Cloud design patterns catalogue](https://learn.microsoft.com/en-us/azure/architecture/patterns/). I checked each of its 44 catalogue entries for the terms “API Management” and “APIM”. Seven articles explicitly mention API Management; the other catalogue patterns can still be useful, but they do not describe APIM in their article text. Microsoft updates this catalogue, so recheck it before treating this list as current.

## Articles that explicitly mention API Management

| Microsoft article | APIM's role in the article | Local scenario and current coverage |
| --- | --- | --- |
| [Anti-Corruption Layer](https://learn.microsoft.com/en-us/azure/architecture/patterns/anti-corruption-layer) | APIM is the external API façade and handles protocol/exposure concerns. A separate Azure Function owns domain translation between modern and legacy models. The article explicitly cautions that APIM does not itself define the anti-corruption layer. | Implemented in [`examples/architecture-patterns-extra/`](../examples/architecture-patterns-extra/README.md): APIM forwards to an adapter service, which maps a legacy order payload into a stable domain DTO. The adapter—not APIM—owns the semantic translation. |
| [Backends for Frontends](https://learn.microsoft.com/en-us/azure/architecture/patterns/backends-for-frontends) | APIM is the shared perimeter: token validation, monitoring, optional caching, and routing to client-specific BFF services. Each BFF performs client-specific composition and shaping; Azure Monitor observes the path. | Implemented by [`examples/bff/`](../examples/bff/README.md), with direct and two-gateway series topologies. [`tests/test_bff_example.py`](../tests/test_bff_example.py) exercises audience checks, response shaping, the series path, and upstream failures. Supporting BFF containers—not APIM—own client-specific business behavior and data aggregation. |
| [Bulkhead](https://learn.microsoft.com/en-us/azure/architecture/patterns/bulkhead) | APIM rate limits are one front-door control. The article's actual isolation example uses Kubernetes resource limits; APIM throttling alone does not isolate compute, storage, or dependency pools. | The supplemental [`examples/architecture-patterns-extra/`](../examples/architecture-patterns-extra/README.md) config routes each tenant to a distinct backend pool/container with independent breaker state and applies per-container CPU/memory limits. Tests and smoke verify tenant A's pool can fail while tenant B stays healthy. This illustrates service-level resource and fault separation locally, not production capacity isolation guarantees. |
| [Deployment Stamps](https://learn.microsoft.com/en-us/azure/architecture/patterns/deployment-stamp) | APIM can resolve a tenant-to-stamp mapping (the example uses Cosmos DB), set the selected backend URL, and sit behind Front Door/APIM regional instances for global ingress and gateway availability. The stamps remain independently deployed workload copies. | The supplemental [`examples/architecture-patterns-extra/`](../examples/architecture-patterns-extra/README.md) routes two tenant paths to separate local stamp services and backend pools, and verifies an unknown tenant returns 404. It does not model dynamic tenant-map lookup, cross-region failover, stamp lifecycle, or replicated mapping data. |
| [Gatekeeper](https://learn.microsoft.com/en-us/azure/architecture/patterns/gatekeeper) | APIM is the inner gatekeeper: API-specific JWT/authentication, rate limiting, header/response policy, and routing to private backends. The outer Application Gateway + WAF filters internet traffic; Azure networking/private endpoints keep the backend private. | Implemented as the `gatekeeper` API in [`examples/architecture-patterns/apim.json`](../examples/architecture-patterns/apim.json): JWT validation, per-principal rate limiting, and backend forwarding. The supporting `pattern-backends` service provides data; Docker Compose network reachability is only a local topology demonstration, not Azure private networking or a WAF. |
| [Gateway Aggregation](https://learn.microsoft.com/en-us/azure/architecture/patterns/gateway-aggregation) | APIM can make lightweight calls to multiple backends with `send-request`, shape/combine results, and set timeout/error behavior. Microsoft says to move complex domain logic or longer orchestration into a dedicated aggregation service behind APIM. | The `aggregation` API in [`examples/architecture-patterns/apim.json`](../examples/architecture-patterns/apim.json) calls orders and profile sequentially, then returns a combined JSON response. Smoke verifies composition, tracing, upstream 503 and connection failures producing 502, and that no redundant catalog request occurs. It does not demonstrate parallel orchestration. |
| [Gateway Offloading](https://learn.microsoft.com/en-us/azure/architecture/patterns/gateway-offloading) | A gateway centralizes shared concerns such as authentication, throttling, transformations, and monitoring. The article's TLS/WAF example specifically uses Application Gateway; APIM is listed for API-specific concerns. It also says not to put business logic in the gateway. | Implemented as `offloading` in [`examples/architecture-patterns/apim.json`](../examples/architecture-patterns/apim.json): rate limiting, internal response cache, request/header transform, and marker header. Supporting backend still serves catalog content. The repo does not model Azure certificate lifecycle, Application Gateway WAF, multi-instance HA, or Azure Monitor. |

## Useful adjacent catalogue patterns

These are useful when designing APIM-backed systems, but the catalogue article itself does not mention API Management. They are not counted in the seven explicit mentions above.

- [Gateway Routing](https://learn.microsoft.com/en-us/azure/architecture/patterns/gateway-routing) is directly represented by the `routing` API in [`examples/architecture-patterns/apim.json`](../examples/architecture-patterns/apim.json): `/route/catalog` and `/route/orders` share a gateway and select backend operations. The article discusses routing via gateway generally and names Application Gateway/Front Door in its Azure implementation; the simulator's APIM routing is a local analogue.
- [Circuit Breaker](https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker) is a reliability pattern for calls to a failing dependency, but the catalogue entry does not name APIM. Gateway Aggregation recommends explicit timeouts and circuit-breaker behavior; a local `send-request` call or error policy should not be presented as a durable distributed circuit breaker unless it tracks state and recovery across requests.
- [Rate Limiting](https://learn.microsoft.com/en-us/azure/architecture/patterns/rate-limiting) and [Throttling](https://learn.microsoft.com/en-us/azure/architecture/patterns/throttling) describe demand control more broadly. APIM policy examples already cover rate-limit behavior; that does not by itself demonstrate infrastructure bulkheads or backend capacity management.
- [Strangler Fig](https://learn.microsoft.com/en-us/azure/architecture/patterns/strangler-fig) is a natural migration pairing with gateway routing, but the catalogue page does not mention APIM. A migration demo needs a legacy/new backend split and incremental routing behavior to qualify as a pattern demonstration.
- [Asynchronous Request-Reply](https://learn.microsoft.com/en-us/azure/architecture/patterns/asynchronous-request-reply) and [Valet Key](https://learn.microsoft.com/en-us/azure/architecture/patterns/valet-key) are valuable API-facing patterns, but this catalogue's entries do not mention APIM. They require queue/status-resource behavior or scoped direct-storage access respectively; ordinary gateway proxying does not implement them.

## What the local simulator can teach

The simulator can demonstrate request-path behavior through API policies: path-to-API routing, JWT and subscription checks, per-key limits, response caching/transforms, backend callouts, and trace inspection. For the current architecture-pattern fixtures, the gateway applies policy while `pattern-backends` supplies service data. In the BFF example, the gateway validates client-specific audiences and routes; the BFF processes the client-shaped payload; the shared backend supplies catalog data. For aggregation, APIM is responsible only for policy callouts and whatever response construction the shipped policy actually performs; backing endpoints remain supporting services rather than gateway capabilities.

Read the scenario/config and the focused examples/tests before inferring semantics: [gateway-routing tests](../tests/test_routing.py), [policy callout fidelity tests](../tests/test_policy_callouts_fidelity.py), and [BFF tests](../tests/test_bff_example.py). The simulator's XML policy subset is not Azure APIM itself, and one passing local request only confirms the implemented fixture behavior.

## Azure-only responsibilities and limits

The local stack does not reproduce Azure resource provisioning or managed-service guarantees. In particular, do not infer Azure parity for Application Gateway/WAF inspection, Azure private endpoints or VNet isolation, managed identities and Entra token issuance, APIM service tiers/capacity/SLA or multi-region gateways, Front Door global health routing, Cosmos DB tenant-to-stamp mapping/replication, Key Vault certificate/secret lifecycle, Azure Monitor/Log Analytics integration, or Azure deployment-stamp operations. The simulator can model selected HTTP and policy outcomes; surrounding Azure services and the workload remain responsible for network boundaries, durable state, domain translation, compute isolation, and operational resilience.

## Additional high-value patterns to consider

Useful extensions are a dynamic tenant-to-stamp lookup, a gateway-versus-service aggregation boundary showing when composition moves behind APIM, and a strangler-style route split between a legacy and replacement backend. A gatekeeper extension could demonstrate an edge proxy plus APIM plus private backend while clearly labeling that local network reachability does not prove Azure WAF/private endpoint behavior. Bulkhead load and capacity tests could extend the existing failure-isolation scenario.
